# CI/CD

- Where two or more codebases produce artefacts of the same type (e.g., npm packages, container images, Android apps), each stage of their pipelines (e.g., checking a change, releasing) MUST be defined once, in a pipeline that they share and only call. So MUST the configuration that those pipelines need (e.g., the release tool's settings, the checks that a change must pass to merge). A breaking change to a shared pipeline MUST go on a temporary branch until every caller has moved to it.
- A pipeline MUST read whatever its environment already knows (e.g., the default branch, the repository's name, the toolchain's version from the file that developers use locally), rather than hard-code it or take it as a parameter.
- Every external dependency MUST be pinned, including the tools that the pipeline installs and the components that it's made of (e.g., a third-party step, a base image). Where the dependency's ecosystem supports a lockfile, the pin MUST be in it. Otherwise, wherever the publisher can move a version label (e.g., a Git tag), the pin MUST be a content hash (e.g., a commit hash, an image digest), with the version beside it. The exception is a pipeline that the same owner shares, which callers SHOULD run at its latest revision, so that a fix reaches every caller at once. For example, on GitHub, third-party actions are pinned in the workflow lockfile, whereas a shared workflow is referenced at the default branch (e.g., `@main`).
- A bot MUST propose an update to every pinned dependency at least every 7 days, and the update MUST be merged automatically once every required check passes, including one that only the versions of existing dependencies changed. A routine update MUST wait a few days after its release (e.g., 7), so that a malicious release is more likely to be found and pulled before it's adopted. A security fix MUST be proposed as soon as it's released.
- Each credential MUST only be available to the part of the pipeline that uses it, and MUST only grant the permissions that it uses. For example, on GitHub, the token grants nothing by default, each job is granted what it needs, and the checkout doesn't keep the token for later steps.
- Where supported, a pipeline MUST obtain its credentials from the CI platform's identity federation, only for the repository, branch, and environment that may use them. A pipeline MUST NOT use a credential tied to a person's account.
- Whatever runs an unreviewed change (e.g., the checks on a pull request) MUST NOT hold a credential that can change anything beyond the feedback on that change (e.g., a review's comments), since the change could use it for whatever the credential allows (e.g., to push to the repository, publish to a registry, or deploy to a cloud). Where an untrusted party can submit the change (e.g., a pull request from a fork), whatever runs it MUST NOT hold any credential at all until a maintainer has reviewed it (e.g., the infrastructure's preview only runs once a maintainer has approved it).
- Text that an untrusted party controls (e.g., a pull request's title, a branch's name) MUST be passed to the code that uses it as data (e.g., in an environment variable), never interpolated into that code, and that code MUST validate it before using it.
- Whatever holds a credential MUST only run the code that it needs, so that a compromised dependency that's merely installed can't use the credential. In particular, it MUST NOT run its dependencies' install scripts where the package manager can skip them (e.g., with npm's `--ignore-scripts`).
- A pipeline MUST NOT leak sensitive data, whether through its logs, its caches, or the files that it uploads or publishes.
- A pipeline SHOULD only be able to reach the hosts that it needs (e.g., the registries that it pulls from and publishes to), so that a compromised dependency can't send a secret or the code anywhere else.
- Everything that a pipeline runs MUST have a timeout.
- A pipeline MUST NOT wait for a fixed delay: whatever waits for something to happen (e.g., a service to start, an emulator to boot) MUST wait for it to signal that it has.
- A failure that a later attempt could overcome (e.g., a registry's outage, a dropped connection) MUST be retried as close as possible to the operation that failed (e.g., by the package manager, rather than by re-running the pipeline).
- A failed run MUST keep what's needed to diagnose the failure without running it again (e.g., the logs of every process that it started, the test reports, screenshots).
- A build tool committed to the codebase (e.g., Gradle's wrapper) MUST have its integrity verified before it runs.
- Dependency downloads SHOULD be cached, keyed on the lockfile and the toolchain's version. Where an unreviewed change could write to a cache, and the toolchain doesn't verify each entry against the lockfile's hashes, a pipeline that delivers an artefact MUST NOT restore that cache, since the change could have planted a compromised dependency in it.
- A failure on the default branch MUST be reported where the maintainers will see it (e.g., an issue, an email), so that nobody has to watch the pipeline.
- Every system that a pipeline relies on to deliver an artefact (e.g., the source control, the CI platform, a registry) SHOULD keep an audit log of changes to its permissions and secrets, and of every publication, where the maintainers can review it.

## Continuous integration

- A change MUST only reach the default branch by being merged once every required check has passed, including a dry run of its release, on a branch that's up to date with its base, so that nobody, whether a person or an agent, can push to it directly.
- A required check MUST only accept a result from the CI platform that runs it (e.g., on GitHub, a required check that expects a specific app), so that nobody can mark it as passed by reporting the result themselves.
- Every change MUST be checked in three ways before it merges:
  - Deterministic analysis that finds defects in the code, beyond linting and formatting. For example, code duplicated across files, and dangerous patterns, as found by tools such as SonarQube or Semgrep.
  - Reviews by agents, for what no deterministic check can enforce. Each change SHOULD be reviewed by general-purpose agents off the shelf (e.g., GitHub Copilot, CodeRabbit), which can find what nobody thought to check, or what's too specific to codify (e.g., using the AWS SDK correctly). It SHOULD also be reviewed by specialist agents whose instructions the maintainers own, each of which only covers one domain (e.g., the systems architecture, the software architecture, the user experience), so that each examines its domain in depth, against the maintainers' own standards.
  - Functional verification: evidence from CI that the change does what it's meant to, and that it doesn't break what it could plausibly affect. Regression testing MUST focus on what the change could plausibly break, rather than on what it clearly can't affect.
- A rule that a deterministic check can enforce (e.g., every dependency is pinned) MUST be enforced by one, rather than left to a review, since a reviewer, whether a person or an agent, may not apply it every time. Once one does, the prompts of the agents that review changes (e.g., their instructions, the skills they load) SHOULD NOT ask for the rule to be checked, so that their context only holds what no deterministic check enforces.
- Where checks run across a matrix (e.g., of operating systems or runtime versions), those that can't vary across it (e.g., linting) MUST run once, before or after the matrix, rather than in each of its runs.

## Continuous delivery

These apply to every artefact, whether it's published to a registry, submitted to a store, or deployed.

- A merge to the default branch MUST release the artefact automatically if and only if the merge changes what ships (e.g., a runtime dependency), and CI MUST check this before the change merges.
- The version and the release notes SHOULD be derived from the commit history (e.g., from Conventional Commits), rather than set by hand, and the notes MUST fit each destination's limits (e.g., an app store's character limit).
- Every artefact MUST be released exactly as it was tested, rather than built again for the release. Where it can only be signed by the pipeline that releases it, that pipeline SHOULD test the signed artefact before releasing it.
- Every artefact that can be signed MUST be signed, with the CI platform's identity where its consumers can verify one (e.g., keyless signing), rather than with a long-lived key. Where a long-lived key is needed and the destination can hold it (e.g., Google Play), the destination MUST hold it, and the pipeline MUST only hold a credential that the destination can revoke (e.g., an upload key).
- Each release MUST be immutable, with an exact version, and whatever deploys it MUST pin that version, so that each upgrade is a change that's checked like any other.
- A release MUST only become visible once every part of it is published (e.g., each operating system's installer).
- A release MUST NOT start whilst a previous release of the same artefact is still running, so that two releases can't claim the same version, or publish out of order.
- The documentation for each release MUST be published when the release is, wherever the documentation is kept, so that it matches what was released.
