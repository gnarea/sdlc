# Anthropic Claude

- Each model SHOULD be named by its full ID (e.g., `claude-sonnet-5-5`), rather than by an alias (e.g., `sonnet`), since an alias can resolve to an older model (e.g., on some cloud providers).
- A design that mixes models (e.g., a cheaper model for the agents that another delegates to) SHOULD be compared in evals with the strongest of them alone at a lower effort level before it's adopted.
- How much a model thinks MUST be set through its effort level, for each agent, since effort controls thinking more reliably than a prompt does. The level SHOULD be chosen in evals for each model, rather than carried over from another, since the same level means a different amount of thinking on each model.
- A prompt SHOULD NOT also tell the model to think more or less, unless evals show that the line does better than the effort level alone. Asking Fable 5.2 (at `medium` effort and above), Sonnet 5.5, or Haiku 5.5 to think less doesn't reliably reduce their thinking.
- An instruction that's meant to apply broadly MUST say so (e.g., "before every review"), since Claude doesn't extend an instruction to cases that it doesn't name, least of all at `low` effort.
- Emphasis other than the keywords that grade an obligation (e.g., "CRITICAL", "IMPORTANT", text in capitals) SHOULD only be added where evals show Claude under-weighting the instruction, since emphasis makes it over-apply the rule.
- Prompts, skills, tools' parameters, and output schemas (e.g., a `reasoning` field) MUST NOT ask Fable 5.2, Opus 5.5, or Sonnet 5.5 to write out their reasoning, since these models may refuse. They MAY ask for a short explanation, or a summary of what was done.
- Where an agent ends its turn before its work is done, its system prompt SHOULD name the kinds of stop to avoid (e.g., a summary that announces the next step instead of taking it, an offer to carry on, a question that it could answer itself). It SHOULD tell the agent to carry on with whatever doesn't depend on someone's answer, and to work through ordinary obstacles (e.g., an error, a timeout). It SHOULD also name the stops that are wanted: where nothing can move without someone's input, before a step that needs approval, and at an obstacle that someone put there on purpose (e.g., access that was withheld), which the agent SHOULD report without working around it.
- Fable 5.2 and Sonnet 5.5 stop early more often at `low` and `medium` effort, and Haiku 5.5 at `low` effort with a long system prompt. For these models, an instruction to carry on SHOULD be compared in evals with a higher effort level, since both make runs longer and costlier. Opus 5.5 SHOULD only get such an instruction where nobody is there to answer, since it ends some turns on long tasks with a progress report, which only stops a run that nobody attends.
- Where an agent does more than its task needs (e.g., adding tests or docs that nobody asked for, starting its own rounds of review once its checks pass), its system prompt SHOULD tell it to stop and report once the work that it was asked for is done and checked, and to suggest anything more at the end. Where it starts subagents that its task doesn't need, whatever in its prompts invites it to delegate (e.g., a line in a skill) SHOULD be reviewed as well. Sonnet 5.5 adds work that nobody asked for at every effort level, and both it and Fable 5.2 start their own reviews at `xhigh` and `max` effort, sometimes with subagents.
- A prompt that embeds material alongside its instructions (e.g., a template that code fills in with inputs, a brief that includes documents or examples) SHOULD mark off each kind of material with an XML tag of its own (e.g., `<input>`, `<example>`), with the same descriptive names across prompts, nested where the material nests (e.g., each `<document>` inside `<documents>`). The instructions themselves MAY stay in Markdown (e.g., in a skill, an agent's definition, or project instructions).
- Where the embedded material is long (e.g., documents of over 20,000 tokens), it SHOULD come first in the prompt, before the instructions and the question, and each document SHOULD carry its source in a tag of its own (e.g., `<source>`).
- Text that a harness adds to a session (e.g., a message from code that runs after a tool call, a notice between steps) SHOULD be written as facts, and SHOULD come after the last tool result and any message from the user, as text of its own (e.g., a mid-conversation system message, where the platform supports them), since Claude may otherwise take it for a prompt injection.
- Where the harness calls the model itself, a message that a user sends mid-run MUST NOT go inside a tool result, and SHOULD be appended as a text block of its own after the last tool result, in the same user message, since Sonnet 5.5 and Haiku 5.5 may otherwise take it for a prompt injection, and ignore it or ask the user to confirm it.
- Where the harness calls the model itself, the system prompt and the tool list MUST stay identical, byte for byte, throughout a session, and the history MUST only be appended to, since an edit invalidates the cache and the model's earlier thinking, and the API may refuse it. Changes SHOULD go in as messages, and the history SHOULD be compacted by the API, or the session restarted from what's been written down.
- Cybersecurity work SHOULD NOT run on Fable 5.2, whose safeguards block most of it. On the other models, evals of such work SHOULD count how often it's declined, since their safeguards block high-risk dual-use work (e.g., developing an exploit), and at times benign work too, though they allow finding vulnerabilities in source code.
- A request that a model's safeguards decline SHOULD only fall back to another model (e.g., through the API's server-side fallback) where evals show that model doing the job well enough, since the model that it falls back to by default is an older one (e.g., Opus 4.8 for Fable 5.2's cybersecurity declines). Evals SHOULD check which model answered each request, since a run that fell back would otherwise be credited to the model that declined it.

## Fable 5.2

Fable 5.2 SHOULD only run exceptional work that justifies the greatest capability available (e.g., research across many sources that ends in a finished document), and even then, only where evals show Opus 5.5 falling short at its highest effort levels, or Fable 5.2 doing as well for less at a lower one.

Its effort SHOULD start at `medium`, rising to `high` for harder or longer work (e.g., a long unattended run), and falling to `low` where evals show that quality holds. It SHOULD only go to `xhigh` for the hardest long-running work where evals show a gain, and to `max` to measure its ceiling, or for the rare task where time and tokens don't matter.

- Data that mustn't be retained MUST NOT be sent to Fable 5.2, unless Anthropic has expressly authorised the organisation to use it with zero data retention, since Fable 5.2 otherwise requires data to be retained.
- An approval rule or other caution that Fable 5.2 will read (e.g., "never retry", "stop at the first error"), whether in its prompts or in notes or feedback from another session or agent, SHOULD name the exact actions that it covers, with any exception written into the rule itself, and SHOULD be removed once its reason no longer holds, since Fable 5.2 applies such rules as written. Where it still holds back routine work, the prompt SHOULD also name the steps that need no approval (e.g., retrying a call that's safe to repeat).
- An approval that Fable 5.2 receives SHOULD name what it approves (e.g., "Yes, run the migration on the staging database"), rather than only telling it to continue.
- A token budget that a harness shows Fable 5.2 in its prompt (e.g., how many tokens it may use or has left) SHOULD be compared in evals with none, since how much it spends depends on the budget's size: in Anthropic's testing at `high` and `xhigh` effort, removing a large one lowered its cost without making its work worse. This doesn't apply to the API's task budgets, which that testing didn't cover.
- Rules on Fable 5.2's writing style SHOULD NOT set hard limits (e.g., "one instruction per sentence, in 20 words or fewer"), since it follows them so closely that they can make its prose choppy.

## Opus 5.5

Opus 5.5 SHOULD run complex work that calls for autonomy and judgement (e.g., long-running agentic coding, designing a system, reviewing a change, drawing up a plan), where what's wanted is clearer than how to get there, including any work that ingests a large corpus, or that divides work between other agents (e.g., research).

Its effort SHOULD start at `medium`, rising to `high` for harder or longer work, and falling to `low` for routine work where evals show that quality holds. It SHOULD only go to `xhigh` or `max` where evals show a gain.

- Untrusted content SHOULD reach Opus 5.5 through a tool result, rather than in a user message (e.g., pasted into a brief), since it treats whatever is in a user message as coming from the user.
- Where untrusted content can only arrive in a user message (e.g., an email that a person pastes into a chat), each pasted block SHOULD be wrapped in an opening and a closing tag that carry the same random ID, which code generates for each block (e.g., `<pasted_content id="ab12">`), each on a line of its own, and the system prompt SHOULD say that text in those tags may hold instructions that the user didn't write, to be followed only where the user's own message asks. The tags are guidance, rather than a guardrail, since the pasted text can imitate them.
- Where time to first token matters at `low` effort, its system prompt MAY ask it to answer directly without deliberating, which can cut its thinking further, if evals show that quality holds.

## Sonnet 5.5

Sonnet 5.5 SHOULD run well-defined work (e.g., implementing a plan that Opus 5.5 drew up, generating code to a specification).

For agentic work, its effort SHOULD start at `medium` where the task is well specified, and at `high` where it's harder or longer. Where latency matters (e.g., chat), it SHOULD start at `medium` or `low`, and for any other work, at `high`. It SHOULD only go to `xhigh` or `max` where evals show a gain.

- A prompt that Sonnet 5.5 will run at `low` or `medium` effort MUST state every step that it must take as an obligation, tied to the task that triggers it, since at those levels it often skips a step that it's only told to take (e.g., loading a skill that it's told to use), and at `low` effort it often answers without thinking.
- A prompt SHOULD NOT discourage Sonnet 5.5 from using tools or skills in general terms (e.g., "minimise tool calls"), since it follows such lines literally. A tool to avoid SHOULD be named, along with when to avoid it.
- Where Sonnet 5.5 runs with adaptive thinking and answers through structured outputs to a task that needs some working out (e.g., totalling figures from a document, ranking items), its system prompt MAY end with "Think the problem through before you answer.", if evals show a gain, since it often answers such tasks without thinking first. At `high` effort, the line brings its accuracy close to that at `xhigh`, for a modest increase in tokens.
- A harness SHOULD NOT add text after every tool result (e.g., a countdown of the tokens left, instructions for each step), since Sonnet 5.5 may then take text there, including a user's messages, for a prompt injection.

## Haiku 5.5

Haiku 5.5 SHOULD only run narrow, well-defined work (e.g., searching, summarising, extracting, classifying, routing) that doesn't need it to gather much context, or to gather it in complicated ways.

Its effort SHOULD start at `medium`, falling to `low` for short, simple, high-volume requests, and rising to `high` for longer work or strict instruction following. It SHOULD only go to `xhigh` or `max` where evals show a gain over Sonnet 5.5.

- A harness that gives Haiku 5.5 a search tool SHOULD also give it today's date, set once when the conversation starts (e.g., in the system prompt, or in the tool's description), since it then grounds its answers in recent results. Where the conversation carries on into another day, the new date SHOULD go in the newest turn. Where it runs at `low` effort with a long system prompt, the system prompt SHOULD also tell it to search for facts that may have changed since its training (e.g., prices, versions), since it otherwise skips searches that it needs.

## Claude Code

- Each skill in an agent's `skills` field SHOULD be qualified by its plugin (e.g., `sdlc:escalation`), since an unqualified name may resolve to another plugin's skill.
- Where falling back to another model isn't wanted, `switchModelsOnFlag` SHOULD be set to `false`, since Claude Code otherwise re-runs a declined request on another model, and keeps the session on that model. Claude Code ignores that setting in subagents before version 2.1.318, so with those versions, `availableModels` SHOULD also leave out the models that it falls back to.
